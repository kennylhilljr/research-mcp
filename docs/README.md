# Documentation map

Agents read this map instead of searching for files. It has three views, kept separate on purpose: the **organizational scope map** (L0 to L3), the **delivery artifact index** (every document, its scope, its source and its status), and the **approval workflow** (the checkpoints a document passes). The two tables between the markers are generated by `node tools/sdd/cli.mjs docmap`; the rest is written by people.

L0 to L3 are organizational scope levels only. Documents are artifact types in an unnumbered chain, and Gates 1 to 3 are approval checkpoints; neither corresponds to a scope level.

## Approval workflow

| Checkpoint | What is approved | Approver (default role) | Folder |
| --- | --- | --- | --- |
| Intake checkpoint (local control) | The problem framing, PRD Section 1 | Product authority | `prd/` |
| Gate 1 | The Product specification: parent and component PRDs | Product authority, with feasibility and control reviewers | `prd/`, `prd/components/` |
| Gate 2 | The high level design (SPEC) and its ADRs | Engineering authority; Product confirms any effect on outcomes | `spec/`, `adr/` |
| Gate 3 | The low level design: contracts, schema, authorization, test strategy | Business Application, component and control owners | `lld/`, `contracts/`, `test/` |
| Code review | Code, tests and the handoff | Engineering reviewers | `build/` |
| Security review | Changes to access, secrets, keys or network exposure | Security reviewers | any |
| Exceptions | An accepted risk recorded in the test plan's `excepted:` list | The exception authority | `test/` |

A person approves by setting `status: approved` with `approved_by` and `approved` in the front matter. Authority comes from `CODEOWNERS` and branch protection. Research (`research/`), operations (`runbooks/`, `postmortems/`) and derived evidence (`trace/`) are not gated.

## ID scheme

| ID | Example | Defined in |
| --- | --- | --- |
| Parent requirement | `FR-3`, `NFR-1`, `OUT-1`, `INV-1` | Parent PRD |
| Acceptance criterion | `TECH-2` | Component PRD; cited by tests and code with `@spec TECH-2` |
| Story, requirement, NFR, invariant, outcome | `TECH-US-1`, `TECH-FR-1`, `TECH-NFR-1`, `TECH-INV-1`, `TECH-OUT-1` | Component PRD |
| Decision | `ADR 0002` | `adr/` ([index](adr/README.md)) |
| Design section | `SPEC 4.2`, `LLD-tech §3` | SPEC and LLDs |

IDs are never renumbered and never reused. An ID that leaves a PRD is recorded in its ID history table.
