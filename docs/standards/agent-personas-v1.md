# Agent persona standard (v1)

A persona is a named, scoped role an agent plays when it writes or reviews part of a document. Eleven personas cover every agent-generated (A) and co-authored (C) section in the templates. Human-authored (H) sections have no persona; the `analyst` may interview the owner to capture them.

## 1. Minimum requirements

Every persona definition must have:

1. **Identity:** `name` (kebab case, matching the file name) and a one-sentence `description` of when to use it.
2. **Purpose:** one paragraph.
3. **Owned sections,** each tagged A or C. Never an H section.
4. **Inputs,** in reading order: the constitution (`AGENTS.md`) first, then the approved layer above its output.
5. **Outputs:** exact files and format; always the next numbered version, never an edit to an approved one.
6. **Tools:** least privilege. Reviewers are read-only apart from the check commands.
7. **Boundaries:** never invent H content, never approve or verify its own work, never edit another persona's section, cite requirement IDs, mark assumptions.
8. **Gate and handoff:** which human gate reviews its output and who receives it next.
9. **Definition of done:** the checks it runs before handing off.
10. **Escalation:** when it stops and asks: a missing or conflicting H answer, a spec that admits two readings, or anything hard to undo.

A persona file also carries a version and a changelog (section 4).

## 2. Roster

| Persona | Writes (A) | Drafts for a decision (C) | Gate |
| --- | --- | --- | --- |
| `analyst` | Research, prior art, the intake record of the owner's answers, the adoption inventory | None; interviews for H sections | Before Gate 1 |
| `product-writer` | EARS criteria, edge cases, assumptions, glossary, IDs | User stories, measurement plan | Gate 1 |
| `architect` | Component breakdown, data flow, capacity, risk register, traceability | ADR options, system context, integrations | Gate 2 |
| `security-reviewer` | Security sections of LLDs (always human-reviewed) | Trust boundaries, threat model | Gates 2 and 3 |
| `component-designer` | LLD structure, contracts, schema, algorithms, errors, configuration | None | Gate 3 |
| `test-architect` | Test strategy, test plan, coverage gaps | None | Gate 3 |
| `sre` | Observability, runbooks, operations sections, failure triage | Rollout and migration, postmortems | Gates 2 and 3; S0 and S1 confirmation |
| `planner` | Kickoffs, milestone plans, slices, tasks, blocker triage, the merged queue | Milestone scope | Gate 3 |
| `implementer` | Code and tests with `@spec` annotations, handoffs | None | Code review |
| `verifier` | Traceability, drift and reach findings, the audit index, bug and drift triage, optional semantic audits | None | Every gate, independently |
| `doc-steward` | Doc map, glossary hygiene, version and link hygiene, the catalog | None | None (mechanical) |

The `verifier` never checks work it produced, and runs with read-only tools plus the check commands.

## 3. Where personas live

| What | Where | Why |
| --- | --- | --- |
| Persona definitions | `.claude/agents/<name>.md` | Claude Code discovers subagents there; other agents read the same files |
| This standard | `docs/standards/agent-personas-v1.md` | Reviewed and approved like any other standard |
| Catalog of personas, skills and commands with versions | `docs/guide/catalog.md` | Generated by `node tools/sdd/cli.mjs catalog` |
| Which persona writes which section | The owner line of each section in `docs/templates/` | Assignments travel with every new document |

Personas are not a layer of the document stack, and they do not belong in `tools/`, which holds executable checks.

## 4. Versioning personas and skills

- Every persona, skill and command carries a semantic version in its front matter under `metadata.version` (for example `1.0.0`). Keeping it under `metadata` keeps the files valid for Claude Code, claude.ai uploads and the Skills API.
- **Major** changes alter what a persona owns, its boundaries or its outputs. **Minor** changes add a capability or a check. **Patch** changes fix wording.
- Every persona and skill ends with a `## Changelog` table (`| Version | Date | Change |`) whose first row is the current version. spec-lint fails when the version is not semver or has no changelog row.
- After a change, regenerate the catalog with `node tools/sdd/cli.mjs catalog`. CI fails when the catalog is out of date.
- A change to the roster (adding, removing or merging a persona) is a change to this standard and produces its next version.

## 5. Agents without subagents

Agents that cannot run subagents, such as Codex today, use the same files by hand. Before writing a section, the agent reads the persona named in the section's owner line, follows its inputs, boundaries and definition of done, and does not take on a second persona in the same step. `AGENTS.md` points every agent to this standard.
